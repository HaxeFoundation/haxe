# Incremental recompilation tests

Scenario tests for the compilation server: a project is edited step by step,
and every step is compiled twice:

- **warm**: through a compilation server (`haxe --wait`) that has compiled all
  the previous steps;
- **cold**: with a fresh compiler process, in a separate directory containing
  exactly the same files.

The main check is **equivalence**: exit code, compiler messages, program output
and every generated file must be identical between warm and cold. Step
expectations (`@expect-*`) also check that each scenario exercises what it is
meant to.

## Running

```
cd tests/incremental
haxe run.hxml                         # all cases, all targets
haxe run.hxml --filter macros/        # cases whose path contains "macros/"
haxe run.hxml --targets interp        # one target
haxe run.hxml --show-known --verbose  # details of known failures, every compilation
```

Options: `--haxe <path>` (compiler to test), `--args "<args>"` (extra compiler
arguments, e.g. `-D incremental-check-refs`), `--strict-order` (do not sort
compiler messages before comparing), `--invalidate` (notify the server with
`server/invalidate` instead of relying on modification times), `--keep` (keep
the `work` directory), `--check-deps` (check the dependencies recorded by a compiler supporting
`-D dump-fingerprints`), `--vfs watch` (start the servers with `HAXE_VFS=watch`,
so that they watch the file system instead of checking modification times).

Some expectations need compiler features, detected when the runner starts:
`@expect-fingerprint-same`/`-changed` (`-D dump-fingerprints`),
`@expect-retyped` (`server/retyped`) and `@expect-no-fs-calls` (`server/vfs`).
Without them, these expectations are not checked (the summary says how many),
and cases using overlays (`server/overlay`) are reported as `SKIP`.

In CI, the suite runs on Linux as part of the `js` target of `tests/RunCi.hx`
(after the server tests), once with the default server and once with
`--vfs watch`; the runner sets modification times with GNU `touch`.

Targets: `interp` (`--interp`, program output is the compiler output), `js`
(`out/main.js`, run with node) and `hl` (`out/main.hl`, run with `hl` when it
is in `PATH`; otherwise only the generated bytecode is compared and output
expectations are skipped). Running the js output requires `node` in `PATH`.
`--add-target hl` also runs every case on a target that its `@targets` does not
list (expectations about `out/main.js` then fail by design).

## Replaying a repository history

`Replay.hx` compiles every commit of a range of a git repository, warm and
cold, with the same comparison:

```
haxe replay.hxml --repo ../path/to/heaps --hxml heaps.hxml --commits 30 [--ignore-order] [--run]
```

The build file is copied into each checkout (`$DIR` is replaced with the
checkout directory) and must write its outputs to `out/`. `--ignore-order`
compares generated text files as sorted lines.

## Writing a case

A case is a `.hxtest` file under `cases/`:

```
# Description of the scenario.
@targets interp js
@args -D some_define

=== initial
@expect-output value 1
--- Main.hx
class Main {
	static function main() {
		trace("value " + Dep.get());
	}
}
--- Dep.hx
class Dep {
	public static function get() return 1;
}

=== change the body
@expect-output value 2
--- Dep.hx
class Dep {
	public static function get() return 2;
}
```

- Header directives: `@targets`, `@args` (extra compiler arguments), `@main`
  (`none` for no `-main`), `@known-failure [targets] <reason>`, `@real-mtime`.
  The list of `@known-failure` can also name a file system mode of the server,
  `legacy` (the default) or `watch`, e.g. `[js,legacy]`: the case is then
  expected to pass in the other mode.
- Each `=== name` section is a step: directives first (`@args` replaces the
  extra arguments from that step on, `@same-second`), then file blocks
  `--- path` (content up to the next `--- ` or `=== ` line),
  `--- delete path`, `--- delete-dir path` and `--- symlink path target`
  (a symbolic link to another file of the project).
- Expectations: `@expect-success`, `@expect-error <text>`,
  `@expect-warning <text>`, `@expect-no-warning`, `@expect-output <text>`,
  `@expect-no-output <text>`, `@expect-compiler-output <text>`,
  `@expect-file <path> <text>`, `@expect-no-file-content <path> <text>`.

## Modification times

Unless a case uses `@real-mtime`, the runner gives every step its own
modification time, two seconds after the previous one, on changed files and,
when a file is created or deleted, on its directories, so that cases do not
depend on how fast the machine compiles. A step with `@same-second` gets a time a fraction of a second after
the previous step instead (`cases/basic/same-second-edit.hxtest`).

## Macro file dependencies

Files read by macros are not tracked automatically: a macro whose result
depends on a file must declare it with `Context.registerModuleDependency`
(see `cases/macros/macro-reads-file-registered.hxtest` and
`macro-registered-file-outside-classpath.hxtest`). Cases must not read
undeclared files from macros, since warm and cold compilations can then
legitimately differ.

## Known failures

`@known-failure` marks cases that fail with the current compiler. The runner
reports them as `XFAIL`, and as `XPASS` (a failure of the run) when they start
passing, so that the marker is removed when a fix lands. They are bugs of the
current server (warm differs from cold), documented in each case.
